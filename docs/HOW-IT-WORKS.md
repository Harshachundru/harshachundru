# How this profile is built

This repo renders two images into `README.md` that GitHub shows on the
profile page — a skills chart and a 3D contribution graph — and both are
generated by small scripts in this repo instead of a hand-edited SVG or a
third-party GitHub Action. This doc explains how each one works and how to
copy either (or both) into your own `<username>/<username>` profile repo.

```
tech-stack.json  ──generate-tech-stack-svg.js──▶  tech-stack-rings.svg
                                                          ▲
GitHub GraphQL API ──generate-contribution-graph.js──▶  contribution-graph.svg
                                                          │
README.md  ◀───────────────────── embeds both SVGs ──────┘
```

Both pipelines follow the same shape: a **data source**, a **generator
script** (plain Node.js, no npm dependencies), and a **GitHub Actions
workflow** that runs the script and commits the result whenever the data
changes.

## 1. Tech Stack Proficiency Rings

**Files:** [`tech-stack.json`](../tech-stack.json) ·
[`scripts/generate-tech-stack-svg.js`](../scripts/generate-tech-stack-svg.js) ·
[`.github/workflows/tech-stack-rings.yml`](../.github/workflows/tech-stack-rings.yml)

A concentric ring chart, one column per category (Frontend, Backend, ...),
one ring per skill. No account data, no secrets — it only reads a JSON file
you edit by hand.

### Data format

```json
{
  "columns": [
    {
      "name": "Frontend",
      "skills": [
        { "name": "TypeScript", "pct": 88, "color": "#3178C6" }
      ]
    }
  ]
}
```

Add, remove, or re-score a skill by editing this file. Colors are any valid
CSS color.

### How the generator works

Hand-authoring this SVG means recomputing, for every ring, a
`stroke-dasharray` of `arcLength circumference` where
`arcLength = 2π·r · pct/100` — and hand-placing every legend dot. The script
does that instead:

- **Ring radius/spacing** — rings share a fixed radius band (80px outer to
  20px inner) with a natural ~14px step between them. If a column has few
  skills, it uses that natural step (so it doesn't look stretched-out and
  sparse); once a column has enough skills that the natural step would push
  the innermost ring below a legible ~20px radius, the step shrinks to fit
  everything in the band instead — see `ringGeometry()` in the script.
- **Stroke width** — scales down with the step, so a crowded column (e.g.
  8 skills) automatically gets thinner rings instead of overlapping.
- **Legend layout** — 3 or fewer skills get one centered column; more than
  that splits into two columns (first half left, second half right),
  auto-computing how many rows are needed.
- **Canvas size** — width scales with the number of columns (`COLUMN_WIDTH`,
  320px each, defined once in `scripts/layout-config.js` and shared with the
  contribution-graph generator — see below); height grows only if a
  column's legend needs more rows than the default card fits.
- **No title inside the SVG** — the README heading above the image is the
  only title. Baking a second one into the image would just repeat it, and
  it would go stale if you ever changed the heading without touching the
  script.

### Workflow

[`tech-stack-rings.yml`](../.github/workflows/tech-stack-rings.yml) runs on
every push to `tech-stack.json` (or the generator script itself), runs
`node scripts/generate-tech-stack-svg.js`, and commits the regenerated SVG
straight to `main` using the workflow's built-in `GITHUB_TOKEN` — no extra
secret needed, since it never touches your GitHub account data.

### To use this on your own profile

1. Copy `tech-stack.json`, `scripts/generate-tech-stack-svg.js`,
   `scripts/layout-config.js`, and `.github/workflows/tech-stack-rings.yml`
   into your `<username>/<username>` repo.
2. Edit `tech-stack.json` with your own columns/skills/percentages/colors.
3. Add `![Tech stack proficiency rings](./tech-stack-rings.svg)` to your
   `README.md`.
4. Push. The workflow generates `tech-stack-rings.svg` and commits it —
   nothing else to configure.

## 2. GitHub Contribution Terrain (3D)

**Files:**
[`scripts/generate-contribution-graph.js`](../scripts/generate-contribution-graph.js) ·
[`scripts/layout-config.js`](../scripts/layout-config.js) ·
[`.github/workflows/contribution-graph.yml`](../.github/workflows/contribution-graph.yml)

Note this script reads `tech-stack.json` too (just to measure the target
width) — if you're using it standalone, without the tech-stack rings, it
falls back to a plain 3-column width.

An isometric 3D city of the last year of contributions: every day with
commits is a building — taller and brighter (blue-glass hues) the busier
the day — and every quiet day stays open park ground, lightly scattered
with trees, a dog, a kid, or a cyclist.

### Why not a ready-made GitHub Action

Most "3D contribution graph" actions (this repo previously used
`yoshi389111/github-profile-3d-contrib`) need to ask GitHub's GraphQL API
"how many contributions has `<username>` made?" — a query on the **account**,
not on the repository the workflow runs in. The default `secrets.GITHUB_TOKEN`
that GitHub Actions hands every workflow is deliberately scoped to just that
one repo, so GitHub's API refuses that account-level query from it
("Resource not accessible by integration"). The action doesn't error loudly —
it just renders whatever scraps of data it *can* see, which looked like a
near-empty graph (single-digit total contributions) that bore no relation to
reality. Every action in this family documents the same fix: authenticate
with a **personal access token** that has explicit permission to read
account data, not the default token.

This script makes that one authenticated call itself and renders the SVG
itself, so the whole pipeline is a few hundred lines you can read rather than
a compiled third-party action.

### How the generator works

**Step 1 — fetch.** One GraphQL POST to `api.github.com/graphql`:

```graphql
query($login: String!) {
  user(login: $login) {
    contributionsCollection {
      contributionCalendar {
        totalContributions
        weeks { contributionDays { date weekday contributionCount } }
      }
    }
  }
}
```

This returns ~53 weeks × 7 days of `{date, contributionCount}` — the same
data GitHub's own profile calendar is built from.

**Step 2 — project.** Each day becomes one building on an isometric grid,
positioned by `(week index, weekday)` and extruded upward by
`sqrt(contributionCount)` (square-root, not linear, so one huge outlier day
doesn't dwarf every other building into invisibility). Every building is 3
flat polygons — a top face and two shaded side faces — computed by
projecting a cube's 8 corners with the standard isometric formula:

```
screenX = originX + (col − row) · halfTileWidth
screenY = originY + (col + row) · halfTileHeight − height
```

Buildings are drawn back-to-front (increasing `col + row`) so nearer ones
correctly cover farther ones — see `render()` and `barSvg()` in the script
for the full geometry.

A zero-contribution day gets height 0 and no side walls — just a flat top
that merges into its neighbors — so a quiet stretch reads as open park
ground instead of a field of small pillars. Only days with real activity
rise up as buildings.

**Step 2b — populate the park.** Every empty tile is a candidate park lot.
`decorationFor()` seeds a tiny PRNG (`mulberry32`, hand-rolled — no
dependency) from the day's own date string, so the same day always gets the
same result: about 1 in 5 empty tiles gets a tree, dog, kid, or cyclist
(each a handful of `<circle>`/`<line>` shapes, not an image asset), placed
at a randomized point inside the tile. The other 4 in 5 stay open lawn —
enough scattered life to feel lived-in without turning the whole park into
clutter. Because the seed is the date, not `Math.random()`, regenerating the
same data twice draws the same tiny scene both times; only new dates
introduce new trees and passersby.

**Step 3 — match the tech-stack card's width.** Rather than a fixed pixel
size, the tile footprint is solved backwards from a target width: it reads
`tech-stack.json` via `scripts/layout-config.js`'s shared `COLUMN_WIDTH` to
compute exactly what width `generate-tech-stack-svg.js` would produce for
the current column count, then picks `halfW` so `2·MARGIN + (weeks +
7)·halfW` equals that number. The two SVGs are always the same *width*, no
matter how many weeks GitHub returns or how many tech-stack columns you
have. Height is intentionally not matched the same way — `TILE_ASPECT`,
`ACTIVE_MIN_H`, and `MAX_BAR_H` set how much vertical room the city gets to
actually look like a skyline with a park around it, so the contribution
card ends up taller than the rings card. The card background, border, and
empty-lot ("ground") color still use the exact same light/dark tokens as
`tech-stack-rings.svg`, so the two remain one consistent design system
despite the difference in height.

**Step 4 — grow on load.** Buildings don't just appear; each one rises from
ground level in a short (0.9s), staggered animation the first time the page
renders. This is done with SMIL `<animate>` on each polygon's `points`
attribute — not a CSS `transform: scaleY`, because an isometric diamond's 4
corners each sit at a different baseline screen-Y, so a single scale anchor
can't reproduce the shape correctly at every in-between frame. Since every
point is a linear function of height (`isoPoint`'s `y = ... − z`), linearly
interpolating the raw coordinates from their height-0 state to their final
state via SMIL reproduces the exact geometry throughout, not an
approximation. Each building's `begin=` delay is its index in the
already-back-to-front painter's-order list × `GROW_STAGGER_S`, so the grow-in
reads as a wave sweeping across the skyline in the same direction the tiles
are drawn.

SMIL animations (like CSS animations, unlike JS or `:hover`) autoplay fine
even though GitHub renders this SVG as a plain `<img>` — there's no
JavaScript involved and nothing needs to be interactive, it just needs to
start on its own. `fill="freeze"` holds the final frame afterward rather
than looping, and the whole sweep finishes in a few seconds so it reads as
a one-time flourish, not a persistent distraction.

### Getting a token — read access only

The script needs to read your contribution calendar; it never needs to write
anything to your account. Create the narrowest token that allows that:

1. Go to **[github.com/settings/tokens](https://github.com/settings/tokens)**
   → **Generate new token** → **Generate new token (classic)**.
   (Contribution data isn't exposed to the newer fine-grained tokens, which
   are scoped per-repository rather than to account-wide profile data — you
   need the classic type here.)
2. Give it a name you'll recognize later (e.g. `profile-contribution-graph`)
   and whatever expiration you're comfortable with — shorter is safer, you
   can always generate a new one.
3. Under **Select scopes**, check **only `read:user`**. Nothing else —
   no `repo`, no `write:*`, no `admin:*`. This scope can read your public
   profile info and contribution activity; it cannot modify anything on your
   account, so if it ever leaked, the blast radius is "someone can see the
   same contribution graph anyone can already see," not "someone can push
   code or change settings."
4. Click **Generate token** and copy the value — GitHub shows it exactly
   once.
5. **Only ever paste it into GitHub's own secret form** (next step). Never
   into a chat tool, an AI assistant, a commit, an issue, or a script file —
   any of those can end up logged or version-controlled, and a leaked token
   should be treated as compromised (revoke it immediately from the tokens
   page if that happens).

### Adding it as a repository secret

Your repo → **Settings → Secrets and variables → Actions → New repository
secret**. Give it any name — this repo's secret is named
`myprofile_workflow` — and paste the token as the value. Whatever name you
pick, the workflow file has to reference that same name (see below).

### Workflow

[`contribution-graph.yml`](../.github/workflows/contribution-graph.yml) runs
nightly and on demand (`workflow_dispatch`). It maps your secret into the
env var the script reads:

```yaml
env:
  CONTRIB_TOKEN: ${{ secrets.myprofile_workflow }}   # right side = your secret's name
  GITHUB_LOGIN: ${{ github.repository_owner }}
run: node scripts/generate-contribution-graph.js
```

Note there are **two different tokens** involved in this workflow, with two
different purposes:

- `secrets.myprofile_workflow` (your PAT, `read:user` only) — used **only**
  to read contribution data from the GraphQL API.
- The workflow's own built-in `GITHUB_TOKEN` (configured via
  `permissions: contents: write` at the top of the file) — used **only** to
  `git push` the regenerated SVG back into this repo.

The PAT never needs write access because it's never used to push anything.

### To use this on your own profile

1. Copy `scripts/generate-contribution-graph.js`, `scripts/layout-config.js`,
   and `.github/workflows/contribution-graph.yml` into your own
   `<username>/<username>` repo.
2. Create your own PAT (`read:user` only) as above.
3. Add it as a repo secret, named whatever you like, then make sure the
   workflow's `env: CONTRIB_TOKEN: ${{ secrets.<your-secret-name> }}` line
   references that same name — the script itself always just reads an env
   var called `CONTRIB_TOKEN`, however you name the underlying secret.
4. Add `![3D contribution terrain](./contribution-graph.svg)` to your
   `README.md`.
5. Trigger it once manually — **Actions tab → generate-contribution-graph →
   Run workflow** — to generate the first version; after that it refreshes
   nightly on its own.

## Troubleshooting

| Symptom | Likely cause |
|---|---|
| Contribution graph shows near-zero bars | PAT missing, wrong secret name in the workflow, or the PAT was created as a fine-grained token instead of classic |
| Workflow run fails on the `git push` step | The workflow's `permissions: contents: write` block is missing or was overridden by a stricter repo-level Actions setting (Settings → Actions → General → Workflow permissions) |
| SVG doesn't update after editing the data file | Check the **Actions** tab for a failed run; also confirm the file path in the workflow's `paths:` filter matches what you edited |
| "Resource not accessible by integration" in the logs | Something is still using the default `GITHUB_TOKEN` for a GraphQL account query instead of the PAT — this is the original bug this whole setup avoids |
